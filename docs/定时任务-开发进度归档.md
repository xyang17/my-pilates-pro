# 定时任务：MyFitnessPro 开发进度归档

**怎么用**：在 Claude 侧边栏点 **Scheduled** → 新建任务 → 按下面填。

- **标题**：【每两周】MyFitnessPro 开发进度归档
- **排期**：cron `0 15 1,15 * *`（每月 1 号和 15 号下午 3 点。cron 做不到「隔周五」，用 1 号/15 号实现两周一次）
- **任务说明**：把下面分隔线以下的全部内容粘进去

---

帮 Jessica 把 MyFitnessPro 这段时间的开发进度归档进项目的架构决策文档。她是这个项目的教练兼产品负责人，经常忘记记录，所以这个任务的核心价值是**用具体的提交内容帮她回忆**，不是催她自己写。

## 项目位置

- 代码仓库（用 Read/Write/Edit 等文件工具时的路径）：`/Users/jessica/my-fitness-pro`
- 目标文档：`/Users/jessica/my-fitness-pro/docs/TECH_ARCHITECTURE.md`（标题是「MyPilatesPro — Technical Architecture & Decision Log」，是这个项目唯一的里程碑与经验教训文档）
- 用 bash 时路径不一样：连接的文件夹挂在 `/sessions/<当前会话名>/mnt/my-fitness-pro`，具体路径看系统提示里「Shell access」那一节列出的映射，不要硬编码。

项目背景：Next.js 16 App Router + Supabase（项目 id `jbnhwtwnydbnfahtwysx`）+ Vercel，线上地址 myfitnesspro.co。产品是私人教练与学员训练管理平台，有教练端和学员端两套视角。

## 步骤

### 1. 找出上次记录到哪里

在 `docs/TECH_ARCHITECTURE.md` 里找最后一个带日期的章节标题（形如 `## 2026-07-05 → 2026-10-16 — 三个半月开发进度总结` 或 `## 2026-10-16 — ...`），取其中最晚的日期作为起点。

### 2. 读出这之后的全部提交

```
git log --since=<起点日期> --date=short --pretty='%ad %s' --reverse
```

如果提交数为 0，就直接告诉 Jessica「这两周没有新提交，文档不用动」，然后结束，不要为了交差硬写。

如果提交很少（少于 5 个）且都是琐碎修复，也直接说明情况，问她要不要跳过这次、攒到下次一起记。

### 3. 看懂这些提交都干了什么

不要只看提交信息就下笔。对其中改动较大、或者信息写得含糊的提交，用 `git show --stat <sha>` 看看动了哪些文件，必要时读一下关键代码。目标是能用人话说清「这个功能现在是什么样」，而不是把提交信息抄一遍。

数据库如果有变化（新表、新字段、新视图），用 Supabase 工具查一下当前真实结构来核对，不要凭 migration 文件猜。

### 4. 草拟三块内容

按文档里已有的格式写（中文，用表格和小标题，参考前面几个章节的风格）：

**一、功能更新** —— 按产品主线分组（比如 课程 / 动作库 / 训练计划 / 体测 / 约课 / 计时器 / 课时包 / 经营数据 / 学员端 等），每条标日期。写「这个功能现在能做什么」，不是「改了哪个文件」。

**二、稳定性修复** —— 表格形式：时间 | 问题现象 | **根因**。重点是根因，不要写「修复了 xx bug」这种没信息量的话。

**三、经验教训** —— 这一块最重要，也最不能靠 git log 瞎编。

只写你**真有依据**的：比如同一个问题反复提交三次说明第一版没找对根因；某个方案被整个替换掉说明原方案走不通；修复代码里的注释写明了踩坑原因。这些可以直接写。

剩下那些你看得出「这里当时应该纠结过，但看不出结论是什么」的，**不要编**，列成问题去问她。这正是她需要你的地方——她忘了，但你能把具体的点摆到她面前让她回忆。问的时候要具体，比如「09-15 那次把拖动排序改成了上下箭头，是因为手机上不好按吗？还有别的原因？」，不要问「有什么经验教训吗」。

### 5. 给她过一遍

把草稿完整发给她看，并把第 4 步里需要她确认或补充的问题一起列出来（控制在 5 个以内，挑最有价值的问）。

明确告诉她：确认或补充之后你才会写进文档。**不要未经确认就直接改文档。**

### 6. 确认后写入并提交

- 插到 `docs/TECH_ARCHITECTURE.md` 里 `## Troubleshooting Guide` 这一节**之前**（文档末尾的章节都是按这个位置往前插的）
- 章节标题格式：`## <起始日期> → <截止日期> — <一句话概括>`
- 同时把文档开头的 `**Last Updated:**` 改成今天
- 如果这期间发现文档上半部分（表结构数量、API 状态、部署状态、排期表）又过期了，在新章节开头加一个过期提醒，但不要擅自重写原文
- 提交：`git add docs/TECH_ARCHITECTURE.md && git commit -m "docs: 补齐 <日期区间> 开发进度与经验教训"`
- **不要 push**，沙箱没有 SSH key 推不上去。提交完告诉她在终端自己跑一下 `git push`。

## 口吻

她中文沟通，回复简洁直接，不要写长篇铺垫。她很在意数据准确——宁可说「这块我看不出来，你记得吗」，也不要给一个听起来合理但没依据的说法。
